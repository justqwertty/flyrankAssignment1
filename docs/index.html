Which content should a reviewer refresh first?

A client-held-out comparison of a transparent rule and a learned ranking model for content-refresh review.

Omar Hisham · August 2026 · Repository

AbstractDataMethodResultsPlaybook

Abstract

Given limited reviewer capacity, which existing content items should be reviewed first for a potential refresh? I evaluated a transparent weighted rule and three learned classifiers on an anonymized 30,000-item FlyRank starter release, then used their scores only to rank a review queue. The primary comparison uses a client-held-out test set and Precision@50, so every model and the baseline are judged on the same unseen items. The selected random forest measured Precision@50 of 0.74 versus 0.24 for the rule baseline, while the held-out declining-label base rate was 0.54. This is decision-support evidence for triaging human review against this proxy label—not evidence that a refresh causes traffic recovery or that the model predicts a search engine’s ranking system.

Introduction / problem statement

A content team may only have 50 review slots in a cycle. The useful output is therefore not an automatic publishing decision; it is a ranked shortlist with reasons a reviewer can inspect. A false positive consumes limited editorial time, while a false negative can leave a declining item unnoticed. I frame the task as ranking items for review and use Precision@50—the share of worthwhile candidates among the first 50—as the decision-aligned metric.

Data

This paper uses the repository’s bundled anonymized FlyRank ML Internship starter release: 30,000 pseudonymized content items across 32 pseudonymized clients. One row represents one content item; activity fields are trailing-90-day aggregates, with recent and preceding 30-day comparison windows embedded in the release. The full internship warehouse is approximately 79 million daily-performance rows, but its aggregate results are not claimed here.

I retained observable search, engagement, content-age, freshness, length, and broad content-context fields. I excluded client and content identifiers from features (they are used only for grouping the split), and excluded titles, domains, URLs, keywords, raw queries, provider/model fields, product decision flags, trend_direction, trend_pct, and all current-window outcome columns. The last set would reconstruct the label and create leakage.

Public-safety note. This page contains aggregate metrics only. It deliberately contains no client names, domains, URLs, titles, raw queries, or row-level records.

Methodology

Label and assumptions

The proxy label is is_declining_label: 1 when the release’s trend_direction is “down,” defined as a more than 20% decline in impressions between its two embedded 30-day windows. It is a contemporaneous, rule-defined proxy—not a future outcome—and must not be mistaken for a causal measure of refresh value.

Features and baseline

The model uses 18 numeric signals (including log-transformed traffic totals, position, age, freshness, CTR, engagement, and scroll rate) and eight categorical/bucketed signals; one-hot encoding yields 52 columns. Missing numeric values are filled with zero and missing categories with “unknown,” matching the reproducible pipeline. The transparent baseline is a weighted score: 40% visibility, 30% freshness risk, 25% position opportunity, and 5% content-depth gap.

Validation and leakage checks

A fixed-seed (42) client-held-out split reserves whole pseudonymized clients for test, leaving 27,675 training rows and 2,325 test rows. Logistic regression, a constrained decision tree, and a random forest are fit on the training partition; selection is by held-out Precision@50. The baseline is scored on that identical test partition. I explicitly excluded label-derived direction/percentage fields and recent-window columns; a deliberate leak test previously drove scores toward perfect, confirming the audit can detect this failure mode.

Results

The random forest was selected on the held-out split. Its lift is meaningful for the queueing task, but it comes from one fixed split and a proxy label; the result should be treated as measured within this release, not as a universal production benchmark.

Limitations & honest framing

  • The label is derived from overlapping historical windows, so the model ranks similarity to a definition of decline; it does not forecast a future recovery or prove that a page needs editing.
  • One client-held-out split, one seed, and 2,325 test rows do not quantify uncertainty. Repeated grouped splits or time-forward validation are required before a firm model-selection claim.
  • Feature importance is associational. It must not be interpreted as a causal explanation of search performance.
  • The result is from the 30,000-row teaching slice. It does not generalize automatically to the ~79M-row warehouse, other clients, or a changing search environment.
  • Human context—brand, accuracy, seasonality, compliance, and editorial quality—remains outside the model and must govern every action.

Ranked recommendations

  1. Run a human review of the top 50 random-forest candidates first. On this split, 37 of 50 carried the proxy decline label, versus 12 of 50 for the rule baseline.
  2. Use reason codes to route the review, not to automate it. Prioritize refresh, then CTR/engagement review, and send all proposed changes through editorial verification.
  3. Keep the transparent baseline as a fallback and monitoring control. It gives reviewers an inspectable counterfactual queue and catches operational drift.
  4. Validate prospectively before production use. Freeze features at a decision date, wait for a future outcome window, and compare reviewer outcomes across repeated client/time splits.
  5. Retrain only after monitoring changes in base rate, Precision@50, and feature distributions. A model that stops outperforming the baseline becomes a review aid to retire, not a result to defend.

Reproducibility

The analysis is reproducible from the public repository’s bundled anonymized starter slice. Run pip install -r requirements.txt, then python scripts/run_all.py; the pipeline writes the model comparison and charts used above. The paper mirror is work/notebooks/capstone.ipynb; supporting notebooks document framing, leakage review, modeling, validation, and the action playbook under work/notebooks. The model seed is 42.
